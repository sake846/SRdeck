# SDRプラグイン・インタフェース仕様書

## 1. 文書情報

- 文書名: SDRプラグイン・インタフェース仕様書
- 対象: `SRdeck` SDRソフトウェア
- ステータス: 現行要件および実装済み標準サービスの外部仕様
- 想定実装環境: .NET / WPF
- 契約方式: 起動時DLL探索。実行中の追加、更新、アンロードは対象外とする

本文中の「必須」は現行契約で満たす要件、「任意」はプラグインが必要に応じて実装する要件、
「将来」は現行版の対象外だが現在の設計で実現を妨げてはならない要件を表す。

## 2. 目的

SDRソフトウェアを基幹部分とプラグイン部分に分離し、新しい受信・復調・解読機能を、基幹部分を変更せず追加できる構造にする。

本仕様の主目的は次のとおりである。

1. SDRデバイス制御と表示処理を基幹へ集約する。
2. 資源管理、実行制御、方式非依存の信号変換を基盤へ集約する。
3. 信号検出、同期、復調戦略、プロトコル解析、固有UIをプラグインへ分離する。
4. プラグインの処理遅延や障害を基幹および他のプラグインから隔離する。
5. 基幹コードを変更せず、起動時に互換性のある外部DLLを検出できるようにする。
6. GUI実行とヘッドレス実行の両方をサポートする。

## 3. 適用範囲

### 3.1 基幹部分

次の機能は基幹が所有する。

- SDRデバイスの検出、初期化、開始、停止および破棄
- IQファイルの再生、開始、停止および再生位置管理
- 中心周波数、サンプルレート、ゲイン、AGCなどのハードウェア制御
- IQ入力バッファおよび信号ブロックの生成
- メインスペクトラム表示
- メインウォーターフォール表示
- 下部の開始・停止、周波数、ゲインおよびSDR制御UI
- プラグインの登録、選択、状態管理および障害処理
- プラグインへのIQ配送
- 任意利用可能な標準チャネル化、レート変換およびサンプル時刻変換
- IQメモリ、ローリングキャプチャ、処理時間など共有資源の上限管理
- 複数の同調要求に対する調停
- 共通音声出力
- 共通設定保存サービス
- 共通ログ、診断およびエラー表示
- プラグイン用UI表示領域とテーマ資源

### 3.2 プラグイン部分

次の機能は各プラグインが所有する。

- 対象方式固有のチャネル選択、信号検出、同期、復調戦略およびデコード
- 標準チャネル処理で方式要件を満たせない場合の独自チャネライザ
- プロトコル解析、復号および重複排除
- 対象方式固有の設定とその検証
- 対象方式固有の受信結果、履歴、集計、エクスポート
- 右側のメインプラグイン画面
- プラグイン固有設定画面
- 必要に応じたスペクトラム上の帯域・マーカー表示
- 必要に応じた復調音声の生成
- プラグイン固有の診断情報

### 3.3 標準サービスと方式固有処理の境界

標準サービス化の判定基準、標準受信経路、個別プラグインが所有する受信判断、および互換方針は
[SDRプラグイン標準サービス設計](plugin-standard-services-architecture.md) に従う。

基盤は標準チャネル処理の利用を全方式へ強制してはならない。標準処理を利用できないホストや、検出器と
チャネライザの融合など方式固有最適化を必要とするプラグインのために、生IQ配送契約を維持する。

### 3.4 現行版の対象外

次は現行版の対象外とする。

- 実行中のDLL追加、更新およびアンロード
- 未信頼プラグインの完全なセキュリティ隔離
- 複数プラグインによる競合する同調要求の自動スケジューリング
- 複数SDRデバイスへの処理の自動割り当て
- プラグイン間の直接通信

## 4. 基本方針

### 4.1 依存方向

依存方向は次の一方向とする。

```text
SdrHost ───────────────┐
                       v
                SRdeckPlugin.Contracts
                       ^
                       │
SRdeckPlugin.<方式A> ──────┤
SRdeckPlugin.<方式B> ──────┘
```

- `SRdeckPlugin.Contracts` は基幹内部型、WPF画面型、特定方式の固有型を参照してはならない。
- 各プラグインは `SRdeckPlugin.Contracts` のみを介して基幹機能を利用する。
- 基幹はプラグインの具体クラスまたはプロトコル固有型を参照してはならない。
- プラグイン同士は相互参照してはならない。

### 4.2 プラグイン識別子

- プラグインは変更されない一意な文字列IDを持たなければならない。
- IDはASCII小文字、数字、ピリオド、ハイフンで構成する。
- 表示名、製品名、ローカライズ名をIDとして使用してはならない。
- 保存済み設定と最終選択状態はIDをキーにする。

IDの例:

| 用途 | ID例 |
|---|---|
| 単一方式 | `example` |
| 複合語 | `example-mode` |
| 提供元による名前空間化 | `vendor.example` |

一つのプラグインが複数の動作方式を提供する場合は、プラグインIDを分割せず、
その内部の安定プロファイルIDとして表現できる。

### 4.3 同時実行

- 現行版では主プラグイン1つと、現在のSDR通過帯域内で動作する0個以上の追加プラグインを同時実行できる。
- 追加プラグインの要求が現在の通過帯域外にある場合、主同調を変更せず追加起動を拒否する。
- 非アクティブまたはストリーム未開始のプラグインへIQブロックを配送してはならない。
- IQ配送キュー、診断、障害隔離、停止処理はプラグインごとに独立させる。
- 競合する同調要求を時間分割する自動スケジューリングは現行版の対象外とする。

## 5. プロジェクト境界

次のプロジェクト境界を採用する。実装済みプロジェクトの一覧は
`docs/plugin-development-guide.md` を参照する。

| プロジェクト | 責務 |
|---|---|
| `SRdeck` | 基幹アプリ、SDR制御、表示、プラグイン管理 |
| `SRdeckPlugin.Contracts` | 基幹とプラグインが共有する安定契約 |
| `SRdeckPlugin.Wpf` | 任意のWPFビュー契約、共通テーマ、共通コントロール |
| `SRdeckCore.*` | 基盤とプラグインが利用する方式非依存信号処理 |
| `SRdeckPlugin.Sdk` | 共通ライフサイクル、連続性追跡、診断、JSON Lines履歴、IQ WAVキャプチャ、ベンチマーク支援 |
| `SRdeckPlugin.<方式名>` | 方式固有のDSP、解析、設定、UI、履歴 |

新しいプラグインも `SRdeckPlugin.Contracts` を参照する独立プロジェクトとして追加する。

## 6. プラグイン能力モデル

プラグインは登録時に、自身が提供する能力を宣言しなければならない。

| 能力 | フラグ | 説明 |
|---|---|---|
| IQブロック受信 | `IqConsumer` | 生IQを処理する |
| 標準チャネルIQ受信 | `ChannelIqConsumer` | 基盤が周波数・帯域・レートを変換したIQを処理する |
| 右側メイン画面 | `MainView` | プラグイン固有の操作・結果画面を表示する |
| 設定画面 | `SettingsView` | プラグイン固有設定を表示する |
| 周波数オーバーレイ | `FrequencyOverlay` | 帯域、チャネル、検出マーカーを表示する |
| ウォーターフォール注釈 | `WaterfallAnnotation` | 復調結果などの時間・周波数位置を表示する |
| ウォーターフォール表示要求 | `WaterfallDisplay` | 時間方向の集約方式と希望表示帯域幅を基幹へ要求する |
| 音声生成 | `AudioProducer` | PCM音声を基幹音声バスへ出力する |
| 共通結果通知 | `ResultPublisher` | 基幹へ受信結果の概要を通知する |
| エクスポート | `Export` | 独自形式の保存機能を提供する |
| ヘッドレス実行 | `Headless` | GUIなしで動作可能な場合だけ設定する |

能力はビット値または固定列挙値として表現できるが、未知の能力を受け取った基幹がプラグイン全体を拒否しない形式にする。

## 7. 基本プラグイン契約

### 7.1 `IPluginModule`

すべてのプラグインが実装する必須契約である。概念上、次の情報と操作を持つ。

| メンバー | 必須 | 説明 |
|---|---:|---|
| `Descriptor` | 必須 | ID、名称、説明、バージョン、互換API、能力 |
| `InitializeAsync` | 必須 | ホストサービスの受領、設定の読み込み、内部準備 |
| `ActivateAsync` | 必須 | 選択されたプラグインとして有効化 |
| `StartStreamAsync` | 必須 | SDRまたは再生ストリームの処理開始 |
| `StopStreamAsync` | 必須 | IQ受付停止と処理キューの終了 |
| `DeactivateAsync` | 必須 | 非アクティブ化、UI更新停止 |
| `DisposeAsync` | 必須 | イベント解除、ワーカー・ファイル・バッファの解放 |
| `State` | 必須 | 現在のライフサイクル状態 |

### 7.2 プラグイン記述子

プラグイン記述子には次を含める。

- プラグインID
- 表示名
- 説明
- プラグインバージョン
- 対応するホストAPIの最小バージョン
- 対応するホストAPIの最大バージョンまたは互換範囲
- 能力一覧
- 作者または提供元
- ライセンス表記
- ヘッドレス対応可否（`PluginCapabilities.Headless`）
- 初期状態で有効にできるか

記述子は初期化前に読み取れる不変データとする。

## 8. ライフサイクル

### 8.1 状態

現行版では次の状態を定義する。

```text
Discovered
    ↓ Initialize
Initialized
    ↓ Activate
Active
    ↓ StartStream
Streaming
    ↓ StopStream
Active
    ↓ Deactivate
Initialized
    ↓ Dispose
Disposed

任意の処理中 ──重大エラー──> Faulted
```

### 8.2 規約

- 非同期ライフサイクル操作はキャンセルトークンを受け取らなければならない。
- `StopStreamAsync`、`DeactivateAsync`、`DisposeAsync` は複数回呼ばれても安全でなければならない。
- ストリーム開始前にIQブロックを配送してはならない。
- ストリーム停止後に新しいIQブロックを配送してはならない。
- 内蔵プラグインとSDK利用プラグインでは、`PluginModuleBase` がライフサイクル操作を直列化する。
  `Streaming` 中のDeactivateまたはDisposeはStop処理を先に完了し、直接の終了でも受信資源を残さない。
- ActivateまたはStartが途中失敗した場合、`PluginModuleBase` はキャンセルされない補償経路で
  DeactivateまたはStopを実行する。停止方向へ遷移した状態は失敗時にも巻き戻さず、後処理だけを再試行可能にする。
- Stop、Deactivate、Disposeの完了時は、基底クラスがプラグイン別AudioキューをResetする。
- Stop開始時は新しいIQ処理を拒否してから、実行中処理との方式固有排他を取得する。
  IQ消費処理は方式固有排他の取得後にも `Streaming` 状態を再確認する。
- ストリーム停止時は、内部ワーカーへの新規投入を停止し、処理中ブロックの完了を待ってから、
  残キューを破棄するか処理完了まで排出する。Stop復帰後に旧ストリームの結果を発行してはならない。
- 停止処理にはホスト設定のタイムアウトを適用する。
- タイムアウトまたは未処理例外発生時、ホストはそのプラグインを `Faulted` として隔離する。
- プラグインの異常でSDRストリーム、スペクトラム、ウォーターフォールを停止してはならない。

### 8.3 ストリーム世代

SDR開始、ファイル再生開始、入力切替、サンプルレート変更など、連続性が失われるたびに基幹は新しいストリーム世代IDを発行する。

プラグインは世代IDが変化した場合、次の状態をリセットしなければならない。

- 復調器の位相・フィルタ履歴
- フレーム同期状態
- ブロック間のサンプル連続性に依存する状態
- 旧世代を参照する遅延処理

受信履歴、ユーザー設定、統計の累積値は、プラグインの仕様に応じて維持してよい。

## 9. ホストサービス

プラグインは初期化時に `IPluginHostContext` を受け取る。次の表は、現行の
`SRdeckPlugin.Contracts` がホストコンテキストから直接公開するサービスである。
API の型とメンバーは Contracts の公開型を正本とし、本節はその意味と利用規約を定める。

| サービス | 責務 |
|---|---|
| ログサービス | プラグインID付きログの記録 |
| 設定ストア | 名前空間化された設定の読み書き |
| UIディスパッチャ | UIスレッドへの安全な処理切替 |
| 同調要求サービス | SDR条件の要求と適用結果通知 |
| 音声出力バス | 復調PCMの出力 |
| 時刻サービス | テスト可能な現在時刻の取得 |
| 通知サービス | 受信通知音の再生。警告・エラーはログとプラグインUIで表現する |
| メトリクスサービス | 方式固有カウンター、ゲージ、処理時間の記録 |
| 実行時診断 | IQ配送、キュー、ドロップ、処理時間および実行バックエンドのスナップショット |
| 受信機テレメトリ | 利用可能な場合のホスト校正済みRFレベル |

次の機能は独立したホストコンテキストサービスではなく、専用契約またはSDKとして提供する。

| 機能 | 現行の提供形態 |
|---|---|
| 共通結果通知 | プラグインが `IPluginResultProvider` を実装してイベントを発行する |
| プラグインデータパス | `IPluginSettingsStore.DataDirectory` を使用する |
| 標準チャネルIQ | `IPluginChannelBlockConsumer` が要求を宣言し、ホストがブロックを配送する |
| サンプル時刻・連続性 | IQメタデータと `ChannelIqBlockMetadata.MapOutputToSource`。追跡補助はSDKの `IqStreamContinuityTracker` |
| メモリ・リース | `IIqBlockLease` および `IChannelIqBlockLease` の呼出し期間限定リース |
| IQキャプチャ | SDKの有界履歴バッファと `BoundedIqWavWriter`。現行Contractsにホストキャプチャサービスはない |

プラグインは記述子のホストAPI互換範囲、任意のコンテキストメンバー、適用結果、Null実装を通じて
利用可能な機能を判断する。旧ホストで標準チャネル経路を利用できないことを理由に、生IQフォールバックを
許可した互換プラグイン、または生IQだけを必要とする互換プラグインを拒否してはならない。

プラグインは `Application.Current`、`MainWindow`、`MainViewModel`、基幹のDIコンテナを直接参照してはならない。

## 10. IQブロックおよびチャネルストリーム配送

### 10.1 基本契約

IQを処理するプラグインは `IIqBlockConsumer` 相当の能力を実装する。

ホストは基幹内部のリングバッファ、読み書きポインタ、可変配列を直接公開してはならない。プラグインには、寿命が管理された読み取り専用IQブロックを渡す。

標準チャネルサービスを利用するプラグインは、対象周波数または入力中心からのオフセット、必要帯域、
希望出力サンプルレートおよび品質方針を要求する。ホストは実際に適用した中心周波数、帯域、出力レート、
群遅延、元入力とのサンプル位置対応を返す。要求を満たせない場合は調整内容または拒否理由を返し、
黙って異なる条件のIQを配送してはならない。

### 10.2 IQブロックの必須メタデータ

| 項目 | 型の要件 | 説明 |
|---|---|---|
| ストリームID | 一意な値 | 入力セッションを識別する |
| 世代ID | 単調増加値 | 連続性が失われた単位を識別する |
| シーケンス番号 | 64ビット整数 | 世代内のブロック順序 |
| 絶対サンプル位置 | 64ビット整数 | ブロック先頭の位置 |
| 単調時刻 | 高精度値 | 遅延・処理時間測定用 |
| UTC時刻 | 日時 | 利用可能な場合の受信時刻 |
| サンプルレート | Hz整数 | 実際の入力サンプルレート |
| 中心周波数 | Hz整数または64ビット整数 | 実際の入力中心周波数 |
| サンプル数 | 整数 | 複素サンプル数 |
| 不連続フラグ | フラグ集合 | ストリーム開始、欠落、同調変更、サンプルレート変更 |
| 入力種別 | 固定識別子 | SDR、IQファイル再生など |

IQデータはメタデータの一部ではなく、リースの `ReadOnlyMemory<Complex32>` として渡す。
現行APIにはサンプル形式識別子を持たせず、`Complex32` を固定の標準表現とする。

### 10.3 サンプル表現

- 現行版のプラグイン契約上の標準形式は、I/Q各成分をおおむね `-1.0` から `+1.0` に正規化した複素32ビット浮動小数とする。
- 正規化基準はホストAPI仕様として固定する。
- ハードウェア固有の整数表現、バイト順序、インターリーブ方式をプラグインに公開しない。
- 将来別形式を追加する場合は、形式識別子と能力ネゴシエーションを用いる。

### 10.4 メモリ寿命

- IQデータはメモリプールを利用したリース方式を基本とする。
- ホストはコールバックの正常、例外、キャンセル完了後にリースを返却する。
- プラグインはコールバック完了後にリースまたはデータを参照してはならない。
- リースをコールバック完了後まで保持または参照してはならない。後続ワーカーで処理する場合は、
  コールバック中にプラグイン所有の有界バッファへ必要量だけコピーする。
- プラグイン所有キューの容量と最大保持時間を制限する。
- 所有キューの上限超過時は方式側で新規ブロックを拒否またはドロップし、基幹ストリームを待機させない。
- ホストは未返却リース数を診断値として記録する。

### 10.5 スレッド規約

- IQ配送はUIスレッドで行わない。
- IQコールバックはホスト管理のプラグイン別ワーカーから呼ばれる。方式固有処理はこのコールバック内で
  完了させるか、有界なプラグイン所有キューへコピーして実行する。
- コールバックの平均処理速度は入力速度以上を維持し、処理時間とキュー滞留を診断できなければならない。
- ホストの入力、FFT、描画、音声処理スレッドを待機させてはならない。
- プラグインのイベントまたはコールバックからホストの可変状態を直接変更してはならない。

### 10.6 バックプレッシャーとドロップ

プラグインごとに容量制限付き配送キューを設ける。

現行版の既定方針は次のとおりとする。

- キュー満杯時は新しいブロックをドロップする。
- ドロップ数を診断値へ加算する。
- 次に受理されたブロックへ `SamplesDropped` 不連続フラグを付ける。
- プラグインへ累積ドロップ数と欠落サンプル数を通知する。
- ドロップ率が警告閾値を超えた場合、ホストUIへ警告を表示する。
- 1つのプラグインの過負荷を理由に、SDR入力または他の基幹処理を停止しない。

プラグインは希望キュー容量を宣言できるが、最終上限はホストが決定する。

## 11. 同調要求

### 11.1 所有権

- SDRデバイスを直接操作できるのは基幹だけとする。
- プラグインはSDRコントローラまたはデバイスAPIを参照してはならない。
- プラグインは同調プロファイルをホストへ要求する。
- ホストはデバイス能力、ユーザー操作、他の要求を考慮して適用可否を決める。

### 11.2 同調プロファイル

同調プロファイルには次を含める。

| 項目 | 必須 | 説明 |
|---|---:|---|
| プロファイルID | 必須 | プラグイン内で安定した識別子 |
| 表示名 | 必須 | UIに表示する名称 |
| 対象周波数 | 必須 | 単一または複数の監視対象 |
| 各対象の帯域幅 | 必須 | 必要占有帯域 |
| 希望中心周波数 | 任意 | プラグイン推奨値 |
| 最小サンプルレート | 必須 | 処理可能な下限。サンプルレート自体は基幹の設定値を使用する |
| 周波数ステップ | 任意 | UI同調の推奨刻み |
| 連続受信要求 | 必須 | 同調中断を許容するか |
| 走査許可 | 必須 | 時分割走査を許容するか |
| 希望ゲイン方針 | 任意 | AGC、手動などの推奨 |

### 11.3 適用結果

ホストは要求に対して次のいずれかを返す。

- `Accepted`: 要求どおり適用
- `Adjusted`: ホストが調整して適用
- `Rejected`: 適用不可
- `Deferred`: 現在は適用せず保留

結果には次を含める。

- 実際の中心周波数
- 実際のサンプルレート
- 実際の受信可能周波数範囲
- 調整または拒否理由

`PluginTuningResult.CenterFrequencyHz` は、SDR入力帯域の実際の中心周波数である。`TargetFrequencyHz`（既定値 `0`）にはホストが実際に同調した対象周波数が格納され、スペクトラム画面クリック等で同調周波数が変更された場合に `AppliedConfigurationChanged` を通じてプラグインへ通知される。プラグインは受信可能性を判定するとき、対象周波数と必要帯域が実際の受信可能周波数範囲に収まることを確認する。

ホストは `AppliedConfigurationChanged` を `RequestAsync` の完了前に同期発火してよい。プラグインは自ら発行した同調要求の適用通知を再入的な再要求として扱ってはならず、同一プロファイルへの再要求ループを防止しなければならない。

プラグインは、要求値ではなく適用結果を基準に処理しなければならない。
プラグインはサンプルレートを指定または変更できない。ホストは基幹側で現在設定されている
サンプルレートを使用し、その値が最小サンプルレートまたは対象帯域の条件を満たさない場合は
同調要求を `Rejected` とする。

### 11.4 ユーザー操作との優先順位

現行版の優先順位は次のとおりとする。

1. ユーザーによる停止・入力切替
2. デバイスの安全制約と能力制約
3. ユーザーによる明示的な周波数・サンプルレート操作
4. アクティブプラグインの同調要求
5. プラグインの希望中心周波数、周波数ステップおよびゲイン方針

ユーザー操作によってプラグイン要求を満たせなくなった場合、ホストはプラグインへ新しい適用結果を通知する。プラグインは「対象が受信範囲外」であることを表示できるようにする。

### 11.5 複数要求の競合

現行版は主プラグイン1つと0個以上の追加プラグインを同時実行できる。主プラグインの要求は
ユーザー操作とデバイス制約の範囲で入力中心を変更できる。追加プラグインの要求は、現在の主入力通過帯域へ
全対象が収まる場合だけ受理し、追加要求のために主同調を変更しない。

- すべての要求はプラグインIDを伴う。
- 非アクティブプラグインの要求は拒否する。
- 競合または通過帯域外の要求は、主同調を黙って変更せず理由付きで拒否する。
- 時分割スケジューリングと複数SDRへの自動割り当ては現行版の対象外とする。

## 12. プラグイン選択と復調モード

- プラグインの選択状態を固定列挙型で保存してはならない。
- 基幹は選択中のプラグインIDだけを管理し、MODE UIでプラグインを切り替える。
- プラグイン内のプロファイルIDと選択状態は、各プラグインが自身の名前空間付き設定へ保存する。
- 新しい方式の追加時に基幹の列挙型、switch文、設定スキーマを変更しない構造にする。
- 一つのプラグインに属する動作プロファイルはプラグインの右ペインUIで選択し、基幹UIへ個別方式を公開しない。
- 「プラグインなし」は基幹予約IDまたは未選択状態で表現する。

保存状態の概念例:

```text
SelectedPluginId  = "example.decoder"
example.decoder/settings.json: SelectedProfileId = "profile-a"
```

## 13. UI統合

### 13.1 UI所有権

基幹はメインウィンドウ、レイアウト、タイトルバー、スペクトラム、ウォーターフォール、下部制御を所有する。

プラグインは次のUIコンテンツを任意で提供できる。

- 右側メインコンテンツ
- プラグイン固有設定コンテンツ
- スペクトラム用周波数オーバーレイ
- ウォーターフォール用注釈
- ウォーターフォールの時間モード・表示帯域幅要求
- 状態概要

### 13.2 右側メインコンテンツ

- 基幹は右側に単一のプラグイン表示領域を用意する。
- アクティブプラグインのコンテンツだけを表示する。
- プラグイン未選択時は基幹の案内画面を表示する。
- プラグイン障害時は基幹のエラー画面へ差し替える。
- プラグインは親Windowのサイズ、終了処理、DataContextを変更してはならない。
- プラグインUIは最小推奨幅と高さを記述できるが、基幹レイアウトを強制してはならない。

### 13.3 ViewとViewModel

- プラグインは自身のViewModelを所有する。
- プラグインViewModelは基幹の `MainViewModel` を継承または参照してはならない。
- 基幹はプラグインViewModelの固有プロパティを参照してはならない。
- 現行版ではWPF `FrameworkElement` またはDataTemplateによる表示を許容する。
- 長期的にはContractsからWPF依存を分離できるよう、UI提供契約を別アセンブリまたは任意能力として扱う。

### 13.4 UIスレッド

- DSPワーカーからUIコレクションやWPFオブジェクトを直接更新してはならない。
- UI更新にはホスト提供のUIディスパッチャを使用する。
- 高頻度イベントはプラグイン側で集約し、画面更新頻度を制限する。
- UIが非表示でもDSP処理に不要なUI更新を継続してはならない。

### 13.5 ヘッドレス動作

- ヘッドレス対応を宣言したプラグインはWPFオブジェクトを生成せず初期化できなければならない。
- UI能力が利用不能でもDSP、ログ、結果保存を継続できる構造にする。
- ヘッドレス非対応プラグインは明確な理由とともに無効化する。

## 14. 表示オーバーレイ

### 14.1 周波数オーバーレイ

プラグイン固有の帯域表示を基幹描画へ直接組み込まず、`IFrequencyOverlayProvider` 相当の契約で提供する。

オーバーレイ項目には次を含める。

- 項目ID
- 開始周波数または中心周波数
- 終了周波数または帯域幅
- 表示ラベル
- 表示色またはテーマ色キー
- 選択状態
- 有効・無効状態
- 強調度
- ツールチップ用概要

規約:

- プラグインは描画APIまたはレンダラーを直接呼び出さない。
- 基幹が現在の表示範囲に合わせて座標へ変換する。
- プラグインは周波数単位の不変スナップショットを返す。
- 更新通知は差分またはスナップショット更新として行い、FFTフレームごとに再生成しない。

受信帯域をスペクトラム画面へ描画する項目では、`Fill` と `Stroke` に
`PluginReceiverBandColors.Primary` / `PluginReceiverBandColors.Secondary`
（`SRdeckPlugin.Wpf`）を使う。
これは共通 WPF スタイルの主・副・補助表示アクセント
（`PluginDisplayAccentPrimaryBrush`、`PluginDisplayAccentSecondaryBrush`、
`PluginDisplayAccentTertiaryBrush`）とは別の色系統であり、両者を流用しない。

### 14.2 ウォーターフォール注釈

復調結果などの時間・周波数位置は `IWaterfallAnnotationProvider` で提供する。各項目は安定ID、
表示時刻、周波数および描画色を持つ。基幹はその位置の1秒上へ目盛り色の下向き三角マーカーを描画する。プロバイダーは最新IQ位置に
対応する `WaterfallReferenceTime` も返し、基幹が履歴時間と表示周波数を座標へ変換する。
基準時刻と項目時刻には同じ入力ストリーム時計を使用し、録音再生でもPCの現在時刻へ
置き換えない。履歴範囲外および表示帯域外の項目は基幹側で描画しない。

### 14.3 ウォーターフォール表示要求

プラグインは `IWaterfallDisplayProvider` を任意実装し、`WaterfallDisplayRequest` を返す。
時間モードは次の3種類とする。

- `Uncompressed`: FFT更新1回につき1表示行とし、複数更新を1行へ集約しない。
  このモードの時間目盛りは、ウィンドウの履歴が90秒以内なら5秒間隔、90秒を超える場合は10秒間隔とする。
- `ThreeMinutes`: 画面全高を180秒とし、必要なFFT更新を各行へ集約する。
- `OneHour`: 画面全高を3600秒とし、必要なFFT更新を各行へ集約する。

`PreferredDisplayBandwidthHz` はHz単位の希望値であり、基幹は現在の入力で表示可能な最小幅から
利用可能帯域幅までに調整する。`null` は拡大なしを表す。プロバイダーがない場合、要求値が
不正な場合、またはプラグイン未選択時の既定は3分・拡大なしである。表示要求の変更時は
時間軸の異なる履歴を混在させず、目盛り、カーソル、注釈も実際の表示時間へ同期させる。

具体的な時間モードと希望帯域幅は方式固有要件としてプラグインが所有する。

## 15. 音声出力

### 15.1 所有権

- 音声デバイスの選択、開始、停止、全体音量、録音は基幹が管理する。
- プラグイン音源の有効化とミュートはプラグインが管理し、基幹の旧受信機スピーカー状態には依存しない。
- プラグインはWindows音声デバイスを直接開かない。
- 音声を生成するプラグインは基幹の音声出力バスへPCMフレームを送る。

### 15.2 PCMフレーム

PCMフレームには次を含める。

- プラグインID
- ストリームID
- シーケンス番号
- サンプルレート
- チャネル数
- サンプル形式
- PCMデータ
- 不連続フラグ
- 任意の音量正規化情報

現行版は1つのアクティブプラグインのみを音声源とする。将来のミキシングを妨げないよう、音声源IDを含める。

## 16. 設定と永続化

### 16.1 名前空間

- 設定はプラグインIDごとの名前空間へ保存する。
- プラグインは基幹の設定オブジェクト全体を受け取ってはならない。
- 他プラグインまたは基幹設定の読み書きを許可しない。

概念上の保存構造:

```json
{
  "schemaVersion": 1,
  "settings": {},
  "secretJsonPaths": []
}
```

### 16.2 スキーマ管理

- 各プラグイン設定はスキーマバージョンを持つ。
- プラグインはサポートする旧バージョンからの移行処理を提供する。
- 移行前に元設定を保全する。
- 移行失敗時は既定値で上書きせず、プラグインを警告状態にする。
- 設定の検証エラーは項目単位でUIへ返せる形式にする。

### 16.3 データ保存

- 受信履歴、地図キャッシュ、録音、CSVなどの大量データは設定ファイルから分離する。
- ホストはプラグインごとのデータディレクトリを提供する。
- プラグインは任意の絶対パスを前提にしてはならない。
- データ形式には可能な限りバージョンを持たせる。

### 16.4 秘密情報

- PSKや復号鍵はログ、診断、例外メッセージへ出力してはならない。
- 現行版で通常設定ストアへ保存する場合も、秘密項目であることをメタデータとして区別する。
- 将来OS資格情報ストアまたは暗号化ストアへ移行できる契約にする。

## 17. 結果通知

プロトコルごとに結果構造が異なるため、詳細結果を共通の固定型へ統合しない。

- 詳細な受信モデル、履歴、一覧、地図表示はプラグインが所有する。
- 基幹または将来の通知・連携機能向けに共通結果概要を任意で発行する。

共通結果概要には次を含める。

- 結果ID
- プラグインID
- 受信日時
- ストリームID
- 種別
- 重要度
- タイトル
- 短い要約
- 周波数
- 信号品質の任意値
- プラグイン固有詳細のスキーマバージョンとJSON

基幹はプラグイン固有JSONの内容を解釈しなくてよい。

## 18. ログ、診断および障害処理

### 18.1 共通診断

IQ処理プラグインについて、ホストは最低限次を収集する。

- 配送ブロック数
- 受理ブロック数
- ドロップブロック数
- 欠落サンプル数
- 現在・最大キュー深度
- 現在・平均・最大処理時間
- 未返却リース数
- 最終処理シーケンス番号
- 最終正常処理時刻
- 最終警告
- 最終例外概要
- 現在のライフサイクル状態
- 標準チャネル処理の入力・出力ブロック数、処理時間、群遅延およびドロップ数

プラグインは対象方式固有の診断値を追加できる。

方式固有診断は、ホストの配送・キュー診断と混同せず、プラグインが所有する。診断スナップショットには必要に応じて
測定時刻、入力・選局、信号、同期、検証・復号の段階、値の単位、累積値の起点、直近評価期間を含める。
結果が 0 件であることだけを障害とせず、入力条件が正常で対象信号を待っている状態を表現できなければならない。

診断のログ、コピー、共通結果概要には、受信本文、復号鍵、秘密設定、個人情報になり得る識別子を既定で含めない。
高頻度の診断値はスナップショットへ集約し、UIやログの更新頻度をDSPイベント頻度から分離する。

#### 18.1.1 診断UI表示規約

診断タブは、通常利用時の縦方向の占有を抑えながら原因調査に必要な値へ到達できるよう、
次の順序と段階的開示を共通とする。

1. 上部固定サマリー
2. リアルタイム処理
3. 入力・選局
4. 信号・チャネル
5. 検出・同期・復調
6. 検証・復号
7. 詳細・デバッグ

上部固定サマリーには、総合状態、現在の処理段階、要約、推奨対応、最終更新時刻、
リアルタイム処理負荷、現在キュー深度、累積ドロップブロック数および監視対象概要を表示する。
その他の区分は既定で折りたたみ、上部固定サマリーを除く領域だけをスクロール可能にする。
生ビット、生バイト、イベントログ、固定DSP定数およびGC統計は「詳細・デバッグ」に配置する。

総合状態は `OverallStatusKind` を正本とし、UIでは次の語彙へ対応付ける。

| 契約値 | 基本表示 | 用途 |
|---|---|---|
| `Idle` | 待機中 | 停止中、入力待ち |
| `Running` | 測定中／監視中 | 入力を処理中だが有効結果待ち |
| `Success` | 正常 | 直近の評価期間に有効結果を取得 |
| `Info` | 情報 | 異常ではない追加通知 |
| `Warning` | 要確認 | 品質低下、設定不一致、過負荷など継続可能な問題 |
| `Error` | エラー | 現在の処理を完了できない問題 |
| `Critical` | 重大 | 回復不能または即時確認が必要な問題 |

「受信中」「入力範囲外」「過負荷」などは基本表示を置き換え得る具体的な状態文であり、
契約値を追加するものではない。
方式固有状態よりも、ホストが検出した最終エラー、入力ドロップ、リアルタイム処理超過、
キュー滞留を優先して表示する。リアルタイム処理負荷は次で定義し、OSのCPU使用率と区別する。

```text
リアルタイム処理負荷 [%] = プラグイン処理時間 [ms] / 入力ブロック時間枠 [ms] * 100
```

数値は100%を超えても切り詰めない。既定の初期判定は75%以上またはキュー滞留を「注意」、
100%以上または入力ドロップ発生を「過負荷」とする。方式固有の信号・同期しきい値は
プラグインが所有するが、負荷の意味と表示形式は変更しない。

「リアルタイム処理」には、処理ステージごとに処理内容、実際の実行先（CPU、GPU、CPU+GPU、
不明）、バックエンド名、現在時間、平均時間および入力時間枠に対する比率を表示する。
ホスト標準チャンネルの周波数変換・フィルター・レート変換は、要求設定ではなく直近ブロックで
実際に使用したバックエンドを表示する。GPUからCPUへフォールバックした場合もCPUとして表示し、
ツールチップにチャネルIDごとのバックエンドを示す。

プラグインは任意能力 `IPluginProcessingDiagnosticsProvider` で、方式固有処理をまとめた
`PluginProcessingStageDefinition` を公開する。処理内容には復調だけでなく、同期、誤り訂正、
フレーム検証およびプロトコル解析のうち同じ実行先で連続して処理する範囲を記載する。
実行先を申告しない外部プラグインは「不明 / 未申告」と表示し、ホストがCPUと推測してはならない。
方式固有処理とホスト標準チャネル処理は、実行先が同じ場合も別ステージ・別時間として計測する。

サンプルレートは `MS/s` または `kS/s` で表示し、利用者向けの経路を
`入力IQ → 中間処理 → 復調入力` の順に示す。CIC、FIRおよび補間・間引き比は詳細値とする。

「入力・選局」には、全プラグイン共通の必須行として **レート変換** と
**IQ入力 → 中間 → 復調レート** を表示する。前者は直近ブロックへ実際に適用した変換の有無と方式の要約、
後者は実効サンプルレート経路である。独立した中間段がない場合も `中間なし` と明示して 3 段の順序を保つ。
要求値しか取得できない場合は実効値として表示せず `—` とする。複数チャネルで経路が異なる場合はチャネル別に示す。
変換器名、CIC段数、FIR係数、補間・間引き比などは「詳細・デバッグ」に分離する。

単一・複数受信を問わず、対象は「監視チャネル」として扱う。複数受信のサマリーには
チャネル数と周波数一覧または最小・最大周波数を表示し、展開後に各チャネルの役割、名称、
対象周波数、入力中心からの偏差、適用出力レートおよび処理状態を表示する。
設定済みであっても実際に処理していないチャネルを、処理中として数えてはならない。

### 18.2 ログ規約

- ログにはプラグインID、重大度、時刻、イベントIDを付ける。
- 高頻度ログは抑制または集約する。
- IQデータ全体、復号鍵、個人情報を既定でログ出力しない。
- 例外は握りつぶさず、ホストのログサービスへ通知する。

### 18.3 障害隔離

- プラグインからの例外を基幹処理スレッドの外へ伝播させない。
- 未処理例外、停止タイムアウト、継続的なリース未返却は重大障害とする。
- 重大障害時はIQ配送を停止し、そのプラグインだけを `Faulted` にする。
- 基幹のスペクトラム、ウォーターフォール、SDR制御は継続する。
- ユーザーへプラグイン名、概要、再有効化の可否を表示する。
- 現行版はプロセス内DLLのため、メモリ破壊などに対する完全隔離は保証しない。

## 19. API互換性

### 19.1 バージョン

- Contracts APIはセマンティックバージョニングに準じる。
- プラグインは対応する最小・最大APIバージョンを宣言する。
- ホストは互換範囲外のプラグインをロードせず、理由を表示する。
- メンバーの削除、意味変更、必須化はメジャーバージョン変更とする。
- 任意メタデータや任意能力の追加は可能な限り後方互換にする。

### 19.2 契約型の制約

Contractsに次を含めてはならない。

- 基幹の具象サービス型
- SDRデバイス固有API型
- 特定方式の型
- `MainViewModel`、`MainWindow` など画面固有型
- 基幹内部のリングバッファ型
- 可変なグローバル設定型

## 20. 登録と検出

### 20.1 現行のDLL探索

- 起動時にアプリのベースディレクトリから `SRdeckPlugin.*.dll` を探索する。
- 読み込んだアセンブリから、公開された引数なしコンストラクターを持つ `IPluginModule` 実装を登録する。
- 内蔵プラグインも基幹からコンパイル参照せず、外部プラグインと同じ探索経路へ配置する。
- API互換範囲外のプラグインは有効化しない。
- 同じIDが複数登録された場合は、どちらも自動選択せずエラーにする。
- 登録順序を表示順や優先度として使用しない。
- 現行ホストの表示順は `Descriptor.DisplayName` で決定し、登録順へ依存しない。

### 20.2 将来の分離と信頼性

現行契約は次の将来要件を妨げてはならない。

- コード実行前に読めるマニフェスト
- API互換性、ID、バージョン、署名の事前確認
- 有効・無効設定
- 信頼済み発行元の確認
- プラグイン単位のロードコンテキスト

実行中の更新・アンロードは別仕様とする。

## 21. セキュリティ

- 現行版のプロセス内プラグインは、信頼されたローカルコードのみを対象とする。
- プラグインにはプロセス内コードと同等の権限があるため、Contractsだけで完全な隔離を保証できない。
- プラグインがネットワーク、任意ファイル、外部プロセスを利用する場合は、能力または権限として将来宣言可能にする。
- 第三者配布を行う段階では、署名検証、許可一覧、別プロセス実行を検討する。

## 22. 複数プロファイルを持つプラグイン

一つのプラグインが複数の動作方式を提供する場合は、基幹のプラグインIDを増やさず、
`IPluginProfileProvider` の安定プロファイルIDで表現する。プロファイルの選択UI、方式固有設定、
安全な処理状態のリセット、および選択状態の保存はプラグインが所有する。

ストリーミング中にプロファイルを切り替えられる実装だけが `ILivePluginProfileProvider` を宣言する。
それ以外の実装は停止、選択、再同調、再開を明示的に行い、旧プロファイルの結果を再開後に発行しない。
ホストは方式固有のプロファイルIDや設定項目を解釈しない。

## 23. 性能要件

- プラグイン未選択時に、プラグインIQ配送による継続的なコピーやワーカー負荷を発生させない。
- IQ配送のためにSDR入力コールバックを待機させない。
- スペクトラムとウォーターフォールの更新周期をプラグイン処理時間に依存させない。
- プラグインキューとメモリ使用量に上限を設ける。
- プラグインの平均処理速度が入力速度を下回る状態を診断できる。
- プラグイン停止後、設定されたタイムアウト内にワーカーとリースを解放する。
- UI更新はDSPイベントごとではなく、表示に適した頻度へ集約できる。
- ホットパスの標準サービスは1サンプル単位で呼び出さず、リースされたブロック単位で処理する。
- 定常ブロック処理の割り当て量、コピー回数、最大一時メモリを測定可能にする。
- 標準チャネル処理は入出力サンプル位置と群遅延を報告し、受信時刻の再現性を保つ。

具体的な既定値と調整範囲は26章の運用パラメータに従う。

## 24. テスト要件

### 24.1 Contractsテスト

- プラグインIDと記述子の検証
- API互換性判定
- ライフサイクルの正常・異常状態遷移
- 同じ操作を複数回行った場合の安全性
- キャンセルとタイムアウト

### 24.2 IQ配送テスト

- シーケンス番号と絶対サンプル位置の連続性
- ストリーム世代変更
- サンプルレートおよび中心周波数変更通知
- キュー満杯時のドロップ
- 不連続フラグ
- リース返却と未返却検出
- 遅いプラグインが基幹処理をブロックしないこと

### 24.3 同調テスト

- 要求どおりの適用
- デバイス制約による調整
- 受信範囲外による拒否
- ユーザー操作による要求の上書き
- 非アクティブプラグインからの要求拒否

### 24.4 標準信号処理テスト

- NCO、フィルタ、デシメータ、リサンプラの既知ベクトルとレート変換精度
- IQブロック境界を変更した場合の結果同一性
- 群遅延と入出力サンプル位置の対応
- 世代、不連続、同調・サンプルレート変更時の状態リセット
- 定常処理の割り当て量、コピー回数、最大一時メモリおよび実時間倍率
- 標準チャネルサービスがない場合の生IQフォールバック

### 24.5 UIテスト

- プラグイン切替時の右ペイン差し替え
- プラグイン未選択表示
- Faulted表示
- UIスレッド規約
- ヘッドレス時にWPFオブジェクトを生成しないこと

### 24.6 組み込みプラグイン回帰テスト

各組み込みプラグインは、方式固有の既知ベクトルに加えて、利用する任意契約、設定・履歴移行、
開始・停止の反復、イベント購読解除、結果・エクスポート、およびUI能力のうち該当する境界を検証する。
方式固有の試験項目は各プラグインのプロジェクト内文書またはテスト名で管理し、本仕様へ列挙しない。

## 25. 適合条件

プラグイン基盤とその変更は、次を継続して満たさなければならない。

1. ダミープラグインを追加し、基幹の処理・画面コードを変更せず登録できる。
2. プラグインをIDで選択し、右側画面と設定画面を表示できる。
3. アクティブかつStreaming状態のプラグインだけがIQブロックを受信する。
4. IQブロックに周波数、サンプルレート、時刻、連続性情報が含まれる。
5. 遅いプラグインがSDR入力、FFT、スペクトラム、ウォーターフォールを停止させない。
6. プラグイン例外を捕捉し、そのプラグインだけを停止できる。
7. プラグインの同調要求を基幹が承認、調整または拒否できる。
8. 実際に適用された受信条件をプラグインへ通知できる。
9. プラグイン固有設定を名前空間化して保存・復元できる。
10. プラグインのキュー、ドロップ、処理時間、最終エラーを診断できる。
11. GUIなしで、対応プラグインを初期化・実行・停止できる。
12. 特定方式の具象参照を `CoreEngine`、基幹 `MainViewModel`、`MainWindow` へ導入しない。
13. 既存プラグインの設定・履歴互換処理を当該プラグイン側で維持する。
14. 複数方式を一つのプラグインで提供する場合、安定プロファイルIDで選択できる。
15. 標準チャネル処理を利用するプラグインと生IQを利用するプラグインを同じホストで扱える。
16. 標準信号処理が群遅延、サンプル位置、処理時間、割り当て量を検証可能な形で公開する。

## 26. 運用パラメータ

現行ホストはIQキュー希望値を1～32へ制限し、未指定時は4を使用する。ライフサイクル操作の
既定タイムアウトは5秒である。これらはホスト実装の既定値であり、プラグインABIの意味を固定する値ではない。

ドロップ警告、UI更新間隔、履歴・データ容量などは用途に応じてホストまたはプラグインが上限を持つ。
プラグインは特定の既定値を仮定せず、要求の調整結果と診断値を使用する。
