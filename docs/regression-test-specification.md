# 回帰試験仕様

## 1. 目的と適用範囲

この文書は、ホスト、公開プラグイン契約、SDK、共通信号処理、および各プラグインに共通する
回帰試験の設計、実行区分、合格条件、更新規則を定義する。

実行対象の全件一覧と件数は `SRdeck.Tests/Program.cs` の登録配列を正本とする。
変動する試験名、件数、個別方式のベクトル一覧を本書へ複製しない。現在の一覧は次で取得する。

```powershell
dotnet run --project SRdeck.Tests\SRdeck.Tests.csproj -c Release --no-build -- --list-tests
```

ここでいう回帰試験は、原則として実SDR機器、外部ネットワーク、PCの現在時刻に依存せず、
固定入力、合成IQ、テストダブル、一時ディレクトリで再現できる試験を指す。
物理デバイス、OS、ドライバー、インストーラーへ依存する項目は受入試験として分離する。

## 2. 情報源と所有権

| 情報 | 正本 |
|---|---|
| 実行する試験名、件数、実行関数 | `SRdeck.Tests/Program.cs` |
| 公開APIの型とメンバー | `SRdeckPlugin.Contracts` |
| 契約の意味と適合条件 | `docs/plugin-interface-specification.md` |
| 横断試験の設計規約 | 本書 |
| 方式固有の既知ベクトル、プロトコル境界 | 各 `SRdeckPlugin.<方式名>` のテストコードとプロジェクト内文書 |
| 実機・配布物の確認記録 | リリースごとの受入試験記録 |

試験名を安定した選択キーとして扱う。名称変更時は、関連するCIフィルター、文書、受入手順も同時に更新する。
将来永続的な試験IDを導入する場合は、ランナー登録データへIDを追加し、文書だけにIDを定義しない。

## 3. 共通規約

### 3.1 試験の粒度

1ケースは1つの主たる振る舞いを合否対象とする。統合試験で複数の状態を確認する場合は、
次の順で独立したアサートを置く。

1. 操作の受理、調整、拒否またはキャンセル
2. 最終ライフサイクル状態
3. 外部サービスへの要求内容と回数
4. 永続化された設定または出力
5. DSP、音声、結果、UIの副作用
6. ワーカー、リース、購読、ファイルの解放

アサート失敗メッセージには、対象プラグインまたは要求ID、期待値、実値を含める。
一つの複合条件へ異なる失敗原因をまとめない。

### 3.2 実行区分

| 区分 | 目的 | 実行構成 | 合格判定 |
|---|---|---|---|
| U: 単体 | 純粋関数、固定DSPベクトル、プロトコル変換 | Debug / Release | 常に判定 |
| C: コンポーネント | サービス、状態遷移、キュー、永続化 | Debug / Release | 常に判定 |
| I: 統合 | プラグインとホスト契約、IQ・音声・ビューの連携 | Debug / Release | 常に判定 |
| P: 性能 | 実時間倍率、待ち時間、割り当て量 | Release、デバッガーなし | Releaseのみ判定 |
| A: 受入 | 実機、OS、ドライバー、配布物、長時間安定性 | 指定リリース環境 | 記録付きで判定 |

性能値はウォームアップ後に複数回測定し、中央値とp95を記録する。Debug実行の性能値は参考値とし、
Releaseの合否に代用しない。

### 3.3 テストダブル

同調サービスのテストダブルは、要求履歴、要求回数、現在の適用結果、適用通知回数、
次回要求の拒否または調整を制御できなければならない。

`AppliedConfigurationChanged` は `RequestAsync` 完了前に同期発火し得るケースを必ず含める。
プラグインは自らの要求通知によって再要求ループを起こしてはならない。

時刻依存処理は `TimeProvider`、設定・データ処理は試験ごとの一時ディレクトリを使用する。
非同期設定保存は呼出順に直列化し、遅い先行保存が新しい設定を上書きしないことを検証する。

### 3.4 隔離

標準ランナーは各試験を独立した子プロセスで実行し、試験ごとに一時ディレクトリを分離する。
静的状態、バックグラウンドスレッド、履歴ファイル、環境変数の変更を後続試験へ残さない。

既定の試験時間上限は60秒とする。超過した子プロセスはプロセスツリーごと終了し、
`TIMEOUT` として失敗を報告する。タイムアウトの延長でデッドロックや未解放資源を隠してはならない。

## 4. 横断試験マトリクス

新規プラグインとプラグイン基盤の変更は、該当する次の領域を検証する。

### 4.1 登録と互換性

- DLL名、公開型、引数なしコンストラクターによる探索
- 記述子ID、表示情報、API最小・最大版、能力フラグの妥当性
- 重複ID、互換範囲外、依存DLL欠落、型ロード失敗の隔離
- 基幹から個別プラグイン具象アセンブリへの参照がないこと
- ヘッドレス宣言とWPF依存の整合

### 4.2 ライフサイクル

- Initialize、Activate、Start、Stop、Deactivate、Disposeの正常遷移
- Activate／Start途中失敗時の補償後処理
- Stop、Deactivate、Disposeの反復安全性
- IQ処理とStop／Disposeの競合
- タイムアウト、キャンセル、例外後のFault隔離
- Stop復帰後に旧ストリームの結果、音声、イベントを発行しないこと
- ワーカー、リース、イベント購読、ファイルを残さないこと

### 4.3 IQ配送と標準チャネル

- ストリームID、世代、連番、絶対サンプル位置、UTC／単調時刻の伝達
- ゼロ長、不正メタデータ、非有限値、不連続、入力ドロップ
- キュー満杯時に入力側を待たせず、次ブロックへ不連続を通知すること
- リースの正常・例外・キャンセル経路での返却
- ブロック境界を変えても受信結果が変わらないこと
- 複数チャネルの同期バッチ、要求順序変更、プロファイル変更
- 標準チャネル優先、生IQフォールバック、フォールバック禁止
- CPU／GPU切替後の数値許容差、群遅延、サンプル位置、不連続

### 4.4 同調とプロファイル

- Accepted、Adjusted、Rejected、Deferredの処理
- 適用結果を要求値より優先すること
- 最小サンプルレート不足、通過帯域外、非アクティブ要求の拒否
- 主プラグインと追加プラグインの通過帯域境界
- 同期適用通知、同時要求、完了順逆転、キャンセル
- 安定プロファイルID、未知ID、保存、移行、拒否時ロールバック
- ライブ変更を宣言する場合の安全な再同調とDSP状態リセット

### 4.5 設定、データ、エクスポート、キャプチャ

- 初回、旧スキーマ、未知の新スキーマ、破損JSON、欠落値
- 設定値の正規化、検証、保存順序、保存失敗、キャンセル
- 名前空間外パス、制御文字、巨大入力、書込不能、容量不足
- 秘密値をログ、診断、例外へ出力しないこと
- 空履歴、時間範囲、同時更新、キャンセル、部分書込みを含むExport
- JSON／CSVの件数、文字コード、引用符、改行、Unicode
- IQキャプチャの上限、WAVヘッダー、診断メタデータ、ファイル名衝突
- 保存中のStop／Disposeと失敗後再試行

### 4.6 結果、音声、通知、診断

- 共通結果概要と方式固有JSONのスキーマ版
- 結果と音声に正しいプラグインIDとストリーム情報を付け、通知音を発生元プラグインのホストコンテキストから要求すること
- PCM形式、レート、チャネル、連番、不連続の検証
- 音声無効化、Stop、世代変更時のReset
- 配送数、処理数、ドロップ、キュー深度、処理時間、最終エラー
- 方式固有メトリクスの単位、更新回数、並行更新
- 診断コピーへ受信本文、秘密値、個人識別子を既定で含めないこと

### 4.7 UI

- プラグイン切替、未選択、非互換、Faultedの表示
- UIスレッドへの集約と非表示時の更新抑制
- 大量一覧の仮想化、更新中の選択・スクロール・フォーカス保持
- 700 px、最小高、100～200%表示倍率、長文、未取得値、0件
- キーボード操作、フォーカス表示、アクセシブル名、色以外の状態表現
- 共通テーマキー、直書き色・フォント・共通テンプレート複製の禁止

### 4.8 方式固有処理

各プラグインは、公開規格または検証済み参照データに基づく既知ベクトルを持ち、少なくとも次を検証する。

- 正常な最小フレームまたは受信単位
- 短小、長大、破損、未定義値、訂正限界超過
- 周波数ずれ、タイミングずれ、雑音、隣接妨害のうち方式上重要な境界
- 重複排除、再構成、タイムアウト、ストリーム分離
- 不連続またはプロファイル変更後の再捕捉
- 方式固有設定、履歴、エクスポート、UIの代表経路

具体的なプロトコル名、周波数、符号化パラメータ、試験ベクトルの出典は各プラグイン側で管理する。

## 5. 性能試験

P区分では、機能正しさを別試験で確認したうえで次を測定する。

- 入力時間枠あたりの現在値、中央値、p95処理時間
- 実時間倍率
- 初回と定常の割り当て量
- 最大キュー深度、ドロップ率、回復時間
- CPU／GPU試験では数値誤差と転送・実行・回収時間
- 長時間相当試験ではGC、配列、スレッド、ハンドル、購読、履歴容量の増加

ウォームアップは3回以上、計測は7回以上を既定とする。固定の性能閾値は、対象処理の入力条件、
実行構成、CPU／GPU、許容割り当て量とともにテストコードへ置く。文書だけに閾値を定義しない。

## 6. 受入試験

次は実機・OS・配布環境で確認し、リリース記録へ環境と結果を残す。

- SDRのUSB抜去、再接続、ドライバーエラー、遅延コールバック
- 実オーディオデバイスの初期化失敗、切断、アンダーラン、再オープン
- 物理GPUリセット、ドライバー更新、VRAM不足、CPUフォールバック
- DPI変更、モニター移動、ウィンドウ再生成、長時間ハンドル監視
- x64配布物、依存DLL・ネイティブDLL欠落、API版不一致、ロード例外
- 更新、ロールバック、旧設定移行、ファイルロック、ディスク満杯、電源断相当

受入試験でのみ確認できる項目を、テストダブルの成功だけで完了扱いにしない。

## 7. 標準実行

```powershell
dotnet restore SRdeck.sln
dotnet build SRdeck.sln -c Release --no-restore
dotnet run --project SRdeck.Tests\SRdeck.Tests.csproj -c Release --no-build
```

部分実行と時間上限変更の例:

```powershell
dotnet run --project SRdeck.Tests\SRdeck.Tests.csproj -c Release --no-build -- --filter "Plugin lifecycle"
dotnet run --project SRdeck.Tests\SRdeck.Tests.csproj -c Release --no-build -- --timeout-seconds 120
```

性能失敗時は、実行構成、CPU／GPU、並列負荷、中央値、p95、基準値を報告する。
失敗試験の再実行でも独立プロセスと一時ディレクトリを維持する。

## 8. 更新規則

新しい振る舞いまたは不具合修正を追加するときは、次を同時に確認する。

1. ランナーへの一意な試験名と実行関数の登録
2. 固定入力、合成IQ、テストダブルの前提条件
3. 単一の主目的と、失敗時に判断できるアサートメッセージ
4. 正常、境界、例外、キャンセル、後処理のうち必要な経路
5. 性能試験の場合はRelease限定の根拠、入力条件、基準値
6. 方式固有情報を横断文書へ追加せず、所有プラグイン側へ記録したこと
7. `--list-tests` で新しい試験が表示され、フィルターで単独実行できること

一つの試験が複数の主目的を持つようになった場合は分割する。登録配列から削除した試験を文書だけに残さず、
文書上の固定件数や手書きカタログを再導入しない。
