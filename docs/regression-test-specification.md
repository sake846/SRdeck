# 回帰試験仕様

## 1. 目的と適用範囲

この文書は、ホスト、公開プラグイン契約、SDK、共通信号処理、および各プラグインに共通する
回帰試験の設計、実行区分、合格条件、更新規則を定義する。

本書に検査観点が載っていることと、その試験が実装・実行済みであることは別である。
変更ごとに[試験レビュー記録テンプレート](regression-test-review-template.md)を使い、
要求する振る舞い、適用対象、登録済みケース、アサート、実行証拠を対応付ける。
既存試験で不足する観点は未実装として残し、全試験の成功をもって自動的に充足したと扱わない。

実行対象の回帰試験名、関数、実行順は `SRdeck.Tests/RegressionTestCatalog.cs` の登録一覧を正本とする。
`RegressionSuite`が各項目をxUnit.net v3の個別Theoryケースとして公開する。
変動する試験名、件数、個別方式のベクトル一覧を本書へ複製しない。対象コミットをReleaseでビルドしてから
現在の一覧を次で取得する。古い出力に対する`--no-build`の結果は対象コミットの証拠にしない。

```powershell
dotnet test SRdeck.Tests\SRdeck.Tests.csproj -c Release --no-build --list-tests
```

ここでいう回帰試験は、原則として実SDR機器、外部ネットワーク、PCの現在時刻に依存せず、
固定入力、合成IQ、テストダブル、一時ディレクトリで再現できる試験を指す。
実機の抜差し、OS・ドライバーの実障害、配布・インストール環境そのものの確認は受入試験として分離する。
Windows上のWPF自動試験や、固定入力を使うGPU試験は回帰試験に含み、GPUの環境条件は3.5節で扱う。

## 2. 情報源と所有権

| 情報 | 正本 |
|---|---|
| 回帰試験名、実行順、実行関数 | `SRdeck.Tests/RegressionTestCatalog.cs` |
| 検出される全試験と件数 | `dotnet test --list-tests` |
| 公開APIの型とメンバー | `SRdeckPlugin.Contracts` |
| 契約の意味と適合条件 | `docs/plugin-interface-specification.md` |
| 横断試験の設計規約 | 本書 |
| 方式固有の既知ベクトル、プロトコル境界 | `SRdeck.Tests`内の当該方式の試験・データと、所有プラグインのプロジェクト内文書 |
| 変更に対する適用範囲、未充足観点、実行証拠 | 当該変更のPRまたは変更記録に添付した試験レビュー記録 |
| 実機・配布物の確認記録 | リリースごとの受入試験記録 |

試験名を安定した選択キーとして扱う。名称変更時は、関連するCIフィルター、文書、受入手順も同時に更新する。
将来永続的な試験IDを導入する場合は、ランナー登録データへIDを追加し、文書だけにIDを定義しない。
本書の節番号・検査観点は要求への参照であり、実行可能な試験IDではない。
期待動作は公開契約または所有機能の仕様から決める。実装の現在値をそのまま正解に転記せず、
仕様にない境界の包含関係、拒否・無視・補正方針などは、試験の作成前に所有仕様で決定する。

## 3. 共通規約

### 3.1 試験の粒度

1ケースは1つの主たる振る舞いを合否対象とする。統合試験で複数の状態を確認する場合は、
次の順で独立したアサートを置く。

1. 操作の受理、調整、拒否またはキャンセル
2. 最終ライフサイクル状態
3. 外部サービスへの要求内容と回数
4. 永続化された設定または出力
5. DSP、音声、結果、UIの副作用
6. ワーカー、リース、購読、ファイルの解放

アサート失敗メッセージには、対象プラグインまたは要求ID、期待値、実値を含める。
一つの複合条件へ異なる失敗原因をまとめない。

### 3.2 実行区分

| 区分 | 目的 | 実行構成 | 合格判定 |
|---|---|---|---|
| U: 単体 | 純粋関数、固定DSPベクトル、プロトコル変換 | Debug / Release | 常に判定 |
| C: コンポーネント | サービス、状態遷移、キュー、永続化 | Debug / Release | 常に判定 |
| I: 統合 | プラグインとホスト契約、IQ・音声・ビューの連携 | Debug / Release | 常に判定 |
| P: 性能 | 実時間倍率、待ち時間、割り当て量 | Release、デバッガーなし | Releaseのみ判定 |
| A: 受入 | 実機、OS、ドライバー、配布物、長時間安定性 | 指定リリース環境 | 記録付きで判定 |

性能値はウォームアップ後に複数回測定し、中央値とp95を記録する。Debug実行の性能値は参考値とし、
Releaseの合否に代用しない。

U/C/I/P/Aは試験設計上の区分であり、現行ランナーのCategoryではない。
現行の`Category=GPU`は、`RegressionSuite.Cases`が試験名に`GPU`を含む場合に付与する。
`Category=P`など未実装のフィルターを使わず、必要なケースは検出一覧と完全一致名で確認する。

### 3.3 テストダブル

同調サービスのテストダブルは、要求履歴、要求回数、現在の適用結果、適用通知回数、
次回要求の拒否または調整を制御できなければならない。

`AppliedConfigurationChanged` は `RequestAsync` 完了前に同期発火し得るケースを必ず含める。
プラグインは自らの要求通知によって再要求ループを起こしてはならない。

時刻依存処理は `TimeProvider`、設定・データ処理は試験ごとの一時ディレクトリを使用する。
非同期設定保存は呼出順に直列化し、遅い先行保存が新しい設定を上書きしないことを検証する。
時刻の初期値と乱数seedも固定し、タイムアウト境界は実時間の待機ではなく時計を進めて作る。
OS・機器の挙動を模擬する試験では、実際に注入した故障を記録する。
例えば「存在しない出力先」の失敗だけで、容量不足、アクセス拒否、途中書込み失敗のすべてを検証済みにしない。

### 3.4 隔離

xUnitの`RegressionSuite`は各回帰試験を独立した子プロセスで実行し、試験ごとに一時ディレクトリを分離する。
登録順に直列実行し、試験が失敗しても後続試験を実行する。
静的状態、バックグラウンドスレッド、履歴ファイル、環境変数の変更を後続試験へ残さない。

既定の試験時間上限は60秒とする。超過した子プロセスはプロセスツリーごと終了し、
xUnitの失敗として`TIMEOUT`を報告する。キャンセル時も子プロセスツリーを終了する。
タイムアウトの延長でデッドロックや未解放資源を隠してはならない。
プロセス終了と一時ディレクトリの削除は試験間の隔離であり、製品の資源解放の合格証拠ではない。
製品のStop／Dispose完了後、子プロセスが終了する前にリース数、購読数、ワーカー完了、
ファイルの再オープンなどを検査する。ランナーは一時ディレクトリの削除失敗を握りつぶすため、
終了コード0からファイルロック解放を推定しない。

### 3.5 未実行とGPU検証

xUnitはPassed、Skipped、Failedを区別し、時間上限超過は`TIMEOUT`を含むFailedとして報告する。
GPUが利用できない試験は理由付きのSkippedとし、未実行を成功件数に含めない。
隔離ワーカーの内部プロトコルでは未実行終了コード77を使用する。
不正なフィルターや対象0件の選択を成功扱いにしない。`dotnet test`ではプロジェクトの
`test.runsettings`により`TreatNoTestsAsError`を有効にする。

GPU搭載環境では次を実行する。`SRDECK_TEST_REQUIRE_GPU=1`は子プロセスにも引き継がれ、GPU不足による未実行を失敗にする。

```powershell
dotnet test SRdeck.Tests\SRdeck.Tests.csproj -c Release --no-build --filter "Category=GPU" --environment SRDECK_TEST_REQUIRE_GPU=1
```

`.github/workflows/gpu-validation.yml` は手動実行専用。GPUドライバー、C++ビルドツール、CMakeを備え、
`self-hosted`、`Windows`、`X64`、`srdeck-gpu` のラベルを持つランナーを登録してから実行する。
通常のPR用CIはこの専用ランナーを待たない。ワークフローの追加だけで実GPU検証済みとはみなさない。

### 3.6 ケースごとに固定する仕様

次の情報をテストコード・データまたは所有機能の文書で定義し、レビュー記録から参照できるようにする。
「正常に動く」「適切に拒否」「十分速い」「多数回」「代表値」だけでは試験仕様として扱わない。

| 必須情報 | 記載内容 |
|---|---|
| 対象と目的 | 要求の出典と節、対象モジュール・能力・プロファイル、保護する振る舞いを1つ明示 |
| 前提 | 初期状態、入力源、主／追加プラグイン、設定・スキーマ版、他の動作中モジュール |
| 入力 | 値と単位、長さ、件数、時刻、seed、ブロック分割、ベクトル出典・生成方法。外部データは版・ハッシュも固定 |
| 手順 | 呼出順、反復回数、途中失敗・キャンセルの注入箇所、競合を成立させる同期点 |
| 観測 | 戻り値、状態、要求・通知回数、出力内容と件数、永続化先、資源数、測定区間 |
| 合否 | 完全一致値または許容差、タイムアウトと単位、禁止する出力・副作用、根拠となる仕様 |
| 実行条件 | U/C/I/P/A、Debug／Release、必要機器・ネイティブDLL、判定を変える環境変数 |
| 証拠 | 登録名、ファイル・関数と対象アサート、実行コマンド、TRX・ログ・受入記録 |

浮動小数点は絶対許容差と相対許容差の適用方法、NaN／Infinityの扱いを明記する。
FFT・PCM・画像は比較区間、ウォームアップ除外、群遅延の補正方法も固定する。
同一の実装で入力の符号化と期待値の復号を行う往復一致だけに依存せず、独立した既知値との一致を含める。

### 3.7 境界、競合、組合せの選び方

- 上下限はそれぞれ直前・一致・直後を試す。整数は原則1刻み、時刻は契約の最小分解能、
  浮動小数点は表現可能な隣接値または根拠付きの差分を使い、具体値を入力データへ置く。
- 件数は0・1・上限・上限超過、長さは0・最小未満・最小・最大・最大超過を含める。
  上限を縮小できるテストダブルを使う場合も、本番上限から独立した値で動くことを確認する。
- 列挙値、能力、プロファイル、出力形式は対応値を列挙し、未定義値・非対応の組合せも試す。
  新しい値を追加したら既存の列挙データと比較し、暗黙のdefault分岐で対象から落とさない。
- 非同期処理の「呼出前キャンセル」「処理開始後・完了前キャンセル」「完了後キャンセル」は別経路とする。
  故障も開始前・資源取得後・出力途中を分け、キャンセル後の状態と後処理を個別に判定する。
- 競合はバリアや制御可能なTaskで「Aが処理内部へ到達 → Bを発行 → Aを解放」の順を作る。
  Taskを2つ起動しただけ、またはSleepだけでは、処理区間が重なった証拠にしない。
  完了順が変わる双方の順序を検査し、全待機に上限と失敗時の解放処理を置く。
- 状態を持つ機能では正常値A→正常値B→A、不正入力→正常入力、Stop→再Startを含め、
  旧状態が混入しないことと正常処理へ回復することを確認する。
- 組合せを削減する場合は、全因子・値、実行する組合せ、省略理由を記録する。
  各値を最低1回含め、相互作用する因子の組を含める。故障×停止、世代変更×処理中、
  主／追加×同調、CPU／GPU×不連続など既知の相互作用は単独の代表ケースで代用しない。

## 4. 横断試験マトリクス

以下は最低限の検査観点である。変更ごとに全節を評価し、各観点を「適用」「対象外」に分類する。
適用する行は対象ごと・境界ごとに3.6節のケースへ具体化する。対象外には、未使用の能力、
到達しない状態などの根拠を記録する。「未実装」「実行環境なし」は対象外の理由にしない。
1つの試験が複数の観点を担う場合も、観点ごとに対応するアサートを示す。

### 4.1 登録と互換性

| 検査観点 | 入力・試験方法 | 合格条件・観測点 |
|---|---|---|
| 探索と記述子 | 一時フォルダーへ正常DLLと、命名・公開型・コンストラクター・必須情報を1つずつ不正にしたDLLを配置して探索 | 正常モジュールのID集合が期待値と一致。不正モジュールを登録せず、理由を識別できる |
| 互換性と障害隔離 | API最小／最大の内側・一致・外側、重複ID、依存DLL欠落、型ロード例外を正常DLLと混在 | 契約に従う採否と診断を個別確認。正常DLLは引き続き利用でき、重複した稼働IDがない |
| 能力と任意契約 | 記述子の全能力フラグと実装インターフェースを照合。能力あり／なしの両方をホストから呼ぶ | 提供能力が利用でき、非対応操作は提供されないか規定の非対応結果。新しい能力も照合対象 |
| 依存境界とヘッドレス | 基幹のアセンブリ参照を検査。ヘッドレス宣言のモジュールをビュー未生成で初期化・受信・停止 | 個別プラグイン具象参照が基幹へ入らず、GUI生成やWPF Dispatcherを要求せず完了 |

### 4.2 ライフサイクル

| 検査観点 | 入力・試験方法 | 合格条件・観測点 |
|---|---|---|
| 正常遷移 | Initialize→Activate→Start→Consume→Stop→Deactivate→Disposeの各呼出直後を検査 | 順にInitialized、Active、Streaming、Streaming、Active、Initialized、Disposed。結果・音声も期待件数 |
| 反復と禁止遷移 | Stop／Deactivate／Disposeを各2回。開始前・停止後・破棄後の公開操作。Start→Stopを既定10回 | 反復で余分な通知・保存・解放が起きず、禁止操作は契約の拒否／無視となる。再Startで受信できる |
| 途中失敗とキャンセル | 各ライフサイクル操作の契約上到達できる位置で例外・キャンセル・ハングを注入。特にActivate／Startの資源取得後を含め、正常な別モジュールも稼働 | 戻り値／例外型・最終状態・補償呼出回数が一致。規定のタイムアウトでFaultを隔離し、別モジュールの入力と結果が継続 |
| 実行中の例外 | Consume、結果・音声処理、イベント購読先のそれぞれで例外を発生させる | 例外の報告先とFault化の範囲が契約通り。例外が入力元や無関係のモジュールへ伝播せず、後処理が完了 |
| 処理中の停止・破棄 | Consume内部で待機させてStop／Disposeを発行し、待機を解放。旧世代の遅延コールバックも到着させる | 規定時間内に完了。停止完了後の旧世代の結果・音声・イベントの増分が0 |
| 資源解放 | 正常・失敗・キャンセルの各経路で取得／返却数、購読解除、ワーカー完了、ファイル再オープンを検査 | 未返却・二重返却が0。プロセス終了前にワーカーが終わり、保存先の再利用が可能 |

### 4.3 IQ配送と標準チャネル

| 検査観点 | 入力・試験方法 | 合格条件・観測点 |
|---|---|---|
| 配送とメタデータ | 異なるID・世代・連番・絶対位置・UTC・単調時刻を持つブロックを主／追加モジュールへ配送 | ActiveかつStreamingの対象だけへ配送。各値が一致し、非対象の配送数は0 |
| 不正入力と不連続 | ゼロ長、長さ不一致、不正レート・位置、NaN／Infinity、各不連続要因を1つずつ投入後、正常IQを投入 | 規定の拒否／補正／リセットとなり、非有限値や旧断片が出力へ伝播しない。後続正常データを受信 |
| キュー満杯 | 消費側を停止して容量Kを満たし追加投入、消費を再開して次のブロックを投入 | 新ブロックが待機せずドロップ。深度≦K、ドロップ数・欠落サンプル数が一致し、次の受理ブロックにSamplesDropped。別モジュールは進行 |
| リースと所有権 | 正常・例外・キャンセル時の返却数を追跡。コールバック完了後に元バッファを書き換える | 取得と返却が一致し、二重返却なし。継続処理が必要なデータは所有コピーされ、元バッファの再利用に影響されない |
| ブロック分割 | 同一IQを一括、1サンプル、固定長、端数、固定seedの可変長で投入。同期語・ヘッダー・ペイロードの途中でも切る | 順序・復号値・件数・位置が一致。PCM／DSP値は定義した許容差内。分割による欠落・重複なし |
| 標準チャネルとバッチ | 要求を0・1・複数とし、順序入替・追加削除・プロファイル変更を実施 | 要求IDと出力が一致。同一入力由来の時刻・世代が整合し、削除前の出力やチャネル間混入なし |
| バックエンドと代替経路 | CPU／GPU各経路、標準チャネル利用可／不可、生IQ代替許可／禁止を実行。処理中の切替も行う | 実際に使った経路を検査。禁止時に生IQを使わず、許可時は代替受信可能。切替時の不連続・群遅延・位置と数値差が仕様内 |

「待機しない」は消費側を解放する前に投入呼出が完了することで判定し、補助的な待機上限も固定する。
CPUで成功しただけではGPUの数値一致の証拠にせず、GPU実行を確認できない場合は3.5節に従う。

### 4.4 同調とプロファイル

| 検査観点 | 入力・試験方法 | 合格条件・観測点 |
|---|---|---|
| 適用結果 | Accepted／Adjusted／Rejected／Deferredをテストダブルから返す。要求値と適用値は意図的に変える | DSP・UIは実適用値を使用。拒否・保留を適用済み表示や新設定の保存にしない。理由も一致 |
| レートと入力源 | 主／追加、停止中／受信中、実SDR相当／録音入力、必要レート未満／一致／超過、対応レート有／無 | 主要求は必要なら最小の対応レートへ調整。レート引上げが必要な追加要求・録音入力、未接続・対応レートなしでは契約に従い設定を変えず拒否 |
| 通過帯域境界 | 各対象の中心だけでなく占有帯域の両端を、入力の受信可能範囲の内側・一致・外側へ配置。複数対象の1つだけ外側も試す | 全対象の帯域を使った採否が一致。追加要求で主同調を変えず、非アクティブ要求は拒否 |

## 5. 性能試験

P区分では、機能正しさを確認したうえで次を測定する。対象外の指標は理由を記録する。

- 入力時間枠あたりの現在値、中央値、p95処理時間
- 実時間倍率
- 初回と定常の割り当て量
- 最大キュー深度、ドロップ率、回復時間
- CPU／GPU試験では数値誤差と転送・実行・回収時間
- 長時間相当試験ではGC、配列、スレッド、ハンドル、購読、履歴容量の増加

ウォームアップは3回以上、計測は7回以上を既定とする。固定の性能閾値は、対象処理の入力条件、
実行構成、CPU／GPU、許容割り当て量とともにテストコードへ置く。文書だけに閾値を定義しない。

測定仕様には次を含める。既存試験が異なる方法を使う場合は、実際の方法と本規約との差を記録し、
測定していない指標を測定済みにしない。

1. 入力サンプル数N、レートFs、チャネル数、信号条件、測定対象関数、開始・終了点を固定する。
   入力時間はN/Fs秒とし、複数チャネルを同時に処理する場合に時間をチャネル数倍しない。
2. ウォームアップを集計から除外し、各回の生値を保存する。中央値は昇順中央（偶数は中央2値の平均）、
   p95は昇順の`ceil(0.95 × 計測回数)`番目とする。7回ではp95は最大値であり、長時間の遅延分布の証拠にはしない。
3. 実時間倍率は`入力時間 / 処理時間`（大きいほど速い）と定義する。逆数の処理負荷率を報告する場合は
   `処理時間 / 入力時間`と明記する。合格に必要な余裕倍率はケース側へ数値で置く。
4. 割り当て量は初回と定常を分け、対象スレッド／プロセス、計測API、反復回数、bytes/回またはbytes/入力秒を明記する。
   GPUは投入だけで完了とせず、結果回収までの時間と、必要なら転送・実行の内訳を記録する。
5. 比較試験は同一入力・構成で基準版と変更版を交互に測る。CPU型番、GPU／ドライバー、OS、電源設定、
   バックグラウンド負荷、各閾値、対象コミットを残す。失敗値を捨てて成功回だけ選ばない。

### 5.1 判定を変える設定

| 設定 | 現行の動作 | 記録と判定 |
|---|---|---|
| `SRDECK_TEST_TIMING_ASSERTIONS` | 未指定は有効。`0`／`false`で、このポリシーを参照する時間比較アサートを無効化 | 無効でも試験自体はPassedになり得る。該当時間指標は「未判定」と記録。正しさ・割り当て量等の残る検査とは別に扱う |
| `SRDECK_TEST_REALTIME_BUDGET_MS` | 未指定は100 ms。100～1000の整数で、この設定を参照する応答時間予算を変更 | 実際の値と参照ケースを記録。500 msでの成功を100 msの合格証拠にしない |
| `SRDECK_TEST_REQUIRE_GPU` | `1`／`true`でGPU利用不能を失敗にする | GPU必須の対象・実行バックエンド・Skippedの有無を記録 |
| `SRDECK_TEST_TIMEOUT_SECONDS` | 未指定60秒、1～3600秒で子プロセスの時間上限を変更 | 試験ハング検出の上限であり、製品の処理時間・停止時間の合格閾値に代用しない |

現行の通常CI（`.github/workflows/ci.yml`）はReleaseを実行し、
`SRDECK_TEST_TIMING_ASSERTIONS=0`、`SRDECK_TEST_REALTIME_BUDGET_MS=500`を設定する。
したがって通常CIの成功だけでは、無効化された時間比較や既定100 msでの応答、実GPUの検証は完了しない。
性能へ影響する変更は、判定有効のRelease実行を別途記録する。`Program.cs`の解析・ベンチマーク用コマンドも、
カタログに登録された回帰ケースでない限り通常CIの実行対象には含まれない。

## 6. 受入試験

受入も3.6節のケース仕様を持ち、リリース記録へ実行者・日時、コミットと配布物ハッシュ、
OS／機器型番／ドライバー版／表示倍率、前提設定、手順、期待値、実測値、ログ・画像を残す。
使う環境と数値閾値は実行前に決める。機器がない、操作を再現できない場合は未実行として記録する。

| 項目 | 最低限の操作・条件 | 判定・証拠 |
|---|---|---|
| SDR | 対応する各機器系列で受信中のUSB抜去→再接続→再開を既定3回。ドライバーエラー・遅延通知も評価 | 停止／再開までの実測時間、表示状態、世代、再受信結果が事前の期待値と一致。各機器系列の実行結果を記録 |
| 音声 | 実出力先の初期化失敗、受信中切断、アンダーラン、再オープン | エラーを表示しホスト操作が継続。音声再開の可否・時間、旧音声混入の有無、デバイス解放を確認 |
| GPU | 対象GPU／ドライバーで実GPU経路を確認し、利用不能・リセット・VRAM不足・更新前後を評価 | バックエンド、CPUへの移行、欠落・不連続、回復時間と正しさを記録。実施できなかった故障は別記 |
| 表示と耐久 | 4.7節の倍率・高さで画面確認、異DPIモニター間移動、ビュー再生成。無信号／高トラフィックを各30分以上 | 初期安定後と以降1分ごとのキュー・メモリ・ハンドル・スレッド・履歴容量、操作応答を記録。上限・増加許容値・回復時間を事前固定 |
| 配布 | x64配布物だけを新規フォルダーへ展開して起動・検出・開始停止。依存DLL欠落・API不一致も試す | 使用したZIPの内容・版と起動ログを保存。必要依存が揃い、異常モジュールを隔離して正常機能を使用可能 |
| 更新と保存障害 | 保存済み旧設定で更新→起動→保存→旧版へ戻す。隔離した試験データでロック・容量不足・保存中の強制終了相当を再現 | 対応する移行／ロールバックの範囲に従い値が復元される。非対応版の扱い、既存ファイル保護、再起動後の復旧を記録 |

30分は耐久試験の最低観測時間であり、30分動作しただけでは合格にしない。
要求する連続稼働時間がより長ければ延長する。実機・OS・配布でのみ確認できる項目は、
テストダブルの成功や別機器の成功だけで完了扱いにしない。

## 7. 標準実行

リポジトリルートのPowerShellで実行する。標準の回帰証拠はRelease全件とし、変更した条件付きコンパイルや
Debug固有経路がある場合はDebugも追加する。実行前にコミット、作業差分、`dotnet --info`、5.1節の環境変数を記録する。
以下の各ネイティブコマンドは成功を確認してから次へ進める。

```powershell
dotnet restore SRdeck.sln
if ($LASTEXITCODE -ne 0) { throw 'restore failed' }
dotnet build SRdeck.sln -c Release --no-restore
if ($LASTEXITCODE -ne 0) { throw 'build failed' }

$resultDir = Join-Path 'artifacts\regression' (Get-Date -Format 'yyyyMMdd-HHmmss-fff')
New-Item -ItemType Directory -Path $resultDir -Force | Out-Null
dotnet test SRdeck.Tests\SRdeck.Tests.csproj -c Release --no-build --list-tests |
    Tee-Object -FilePath (Join-Path $resultDir 'discovered-tests.txt')
if ($LASTEXITCODE -ne 0) { throw 'test discovery failed' }
dotnet test SRdeck.Tests\SRdeck.Tests.csproj -c Release --no-build --results-directory $resultDir --logger 'trx;LogFileName=regression.trx'
if ($LASTEXITCODE -ne 0) { throw 'regression tests failed; inspect TRX and console output' }
```

部分実行と時間上限変更の例:

```powershell
dotnet test SRdeck.Tests\SRdeck.Tests.csproj -c Release --no-build --filter "DisplayName~Plugin lifecycle"
dotnet test SRdeck.Tests\SRdeck.Tests.csproj -c Release --no-build --environment SRDECK_TEST_TIMEOUT_SECONDS=120
```

単独選択には`--filter "DisplayName=試験名"`を使う。部分一致は追加ケースの取りこぼしや意図しない選択があり得るため、
選択結果をレビュー記録の予定集合と照合する。部分実行の成功を全件実行の成功と記載しない。

性能判定を有効にして既定の応答時間を確認する場合は、ビルド済みReleaseに次を実行する。

```powershell
dotnet test SRdeck.Tests\SRdeck.Tests.csproj -c Release --no-build --environment SRDECK_TEST_TIMING_ASSERTIONS=1 --environment SRDECK_TEST_REALTIME_BUDGET_MS=100 --logger trx
```

実行記録では次を照合する。

- 予定した登録名の集合、検出された集合、TRXに結果が存在する集合。件数が同じでも名前の入替・漏れは不一致とする。
- Passed、Failed、Skippedの内訳。途中中断や結果なしは未実行、TIMEOUTはFailedとして残す。
- GPU未実行の理由、無効化した性能判定、受入未実行。終了コード0だけでこれらを充足扱いにしない。
- 失敗時の期待値・実値・最初の原因、性能なら構成・負荷・全測定値・中央値・p95・基準値。

再実行でも独立プロセスと一時ディレクトリを維持し、最初の失敗結果を上書きせず保存する。
環境・コード・閾値・選択条件を変えた場合は変更理由を残す。理由不明の成功再試行だけで不安定な試験を解消扱いにしない。

## 8. 更新規則

### 8.1 変更から試験対象を決める

変更者は[試験レビュー記録](regression-test-review-template.md)をPRまたは変更記録へ添付する。
下表は追加検討する範囲であり、表にない変更でも4章全節の適否を評価する。
文書のみなど製品・ランナーの動作を変えない変更では、その根拠を記録して実行試験を対象外にできる。
この場合も、変更したリンク、コマンド構文、記載した仕様と実装の整合を確認し、確認範囲を記録する。

| 変更の入口 | 必ず見直す試験範囲 |
|---|---|
| 新規プラグイン・任意契約・能力 | 4.1～4.8の全観点。能力あり／なし、主／追加、ヘッドレス／UI、配布。対象モジュールを生成する各共通試験へ追加または対象外理由を記載 |
| プロファイル・モード・列挙値 | 全値の正規化・選択・保存・旧値移行、必要レート、ライブ変更、対応DSPベクトル、UI候補と検査用列挙データ |
| SDK・Contracts・共通DSP | 全利用側を参照検索して列挙。各実装の任意契約適合、標準／生IQ、CPU／GPU、共有サービスの例外・停止・不連続 |
| 設定・履歴・Exportの項目や形式 | 初期値・境界・欠落・旧版読込、非既定値の再保存・再起動、全出力形式、秘匿、並行更新・I/O失敗・途中キャンセル |
| 非同期化・キュー・最適化 | 競合する全操作、世代・順序・所有権・キャンセル・停止、未解放資源、処理結果の同値性、性能・耐久 |
| SDR・入力・音声・FFT・表示 | 4.9と利用プラグインの連携、入力源とデバイス能力の違い、稼働中の変更、設定復元、実機・GPU・DPIの該当受入 |
| UI・地図 | 状態・データ件数・操作手段・倍率・高さ、更新中の選択、非表示と再生成、保存復元、オフライン・データ破損 |
| ランナー・CI・依存・配布 | 検出と選択、登録完全性検査の対象、Skipped／TIMEOUT、環境変数、実行構成、配布物だけでの起動、更新・ロールバック |
| 不具合修正 | 元の再現入力と隣接境界、失敗直前の状態遷移、別対象への波及、修正前で失敗・修正後で成功するアサート |

### 8.2 自動検査の保証範囲

現行の`TestRegressionCatalogCompleteness`（`SRdeck.Tests/RegressionTests.Core.TestRunner.cs`）は、
`RegressionTests`と`OneSegRegressionTests`の`public static void Test*()`（引数なし）について登録漏れを検査し、
登録名・登録メソッドの重複も検査する。次の事項はこの検査だけでは検出しない。

- 新しい試験所有クラス、非公開・引数あり・Task戻り値など、探索条件外に作られた試験。
  新クラスを導入する場合は所有クラス集合と適切な呼出方法も更新する。
- メソッド内で列挙しているプラグイン、プロファイル、設定値、故障経路の不足。
  例えば`RegressionTests.AdditionalCoverage.cs`の共通試験用ファクトリーは対象を明示列挙しており、新規プラグインは自動追加されない。
- 試験本体に必要なアサートがない、途中returnで観点を実行していない、既知ベクトルが不足するケース。
- `Category=GPU`の命名条件から漏れたGPU試験、CIで無効化された時間判定、未実施の解析・受入。

したがって、**登録漏れの検査と機能の試験漏れの確認を別々に行う**。
共通試験の名称に「parity」「all」「built-in」が含まれていても全プラグインを網羅している証拠にはしない。
変更した能力の提供側と各試験の実際の対象集合を比較し、差分を追加ケースか理由付きの対象外として解消する。

### 8.3 変更の完了条件

1. 4章の各観点について対象・対象外理由を記録し、適用行を登録名・入力条件・アサートへ対応付ける。
   試験実装状態（既存で充足／追加・修正／未実装）と実行結果（Passed／Failed／Skipped／未実行）を混同しない。
2. 正常・境界・異常・途中キャンセル・競合・回復・後処理の各必要経路を3.6・3.7節の具体値で定義する。
   新しい主目的は独立ケースにし、既存ケースへ条件追加した場合はそのデータとアサートを示す。
3. 新しい試験を`RegressionTestCatalog.cs`へ一意な名前と実行関数で登録する。
   新クラス・能力・プロファイル・対象モジュールについて8.2節の対象集合も更新する。
4. 不具合修正では修正前に意図したアサートで失敗することを確認する。実行できない場合は
   再現ログや入力、確認できない理由を残し、修正前実行済みとしない。
5. 同じ変更内容をビルドし、一覧で新規ケースの検出、完全一致フィルターで単独成功、Release全件結果を確認する。
   性能・GPU・Debug・受入は変更範囲に応じて追加し、予定集合と実行集合の差分を説明する。
6. Failed／TIMEOUT、未実装、必要な試験のSkipped／未実行、無効化した必要指標は未充足として残す。
   保留する場合は影響範囲、理由、担当、実施条件・期限、追跡先を記録し、「回帰確認完了」とは記載しない。
7. レビュー担当はテスト名だけでなく入力とアサート、対象集合、実行証拠を照合する。
   全適用観点に判定証拠があり、未充足がない場合に限り、その変更範囲の回帰確認を完了とする。

登録配列から削除・改名した試験は、参照するフィルター・文書・レビュー記録への影響を確認する。
削除理由と代替試験が守る振る舞いを示し、守られなくなる要求を放置しない。
方式固有情報は所有プラグイン側へ置き、横断文書の固定件数や手書きの全カタログを再導入しない。
